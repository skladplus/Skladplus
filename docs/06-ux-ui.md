# 06 — UX/UI: архитектура интерфейса, конструктор, дизайн-система

Как устроен интерфейс платформы: навигация двух контуров, архитектура-конструктор
(реестры и настройки-как-данные), базовые паттерны, дизайн-система и порядок
реализации. Поведение экранов — `docs/04-product-spec.md`, данные —
`docs/05-domain-draft.md`, распределение работ — `docs/07-workplan.md`.

## 1. Информационная архитектура

Один Next.js app, два layout по контурам; меню генерируется из реестра модулей
(§2), фильтруется ролью и feature-флагом.

**Кабинет клиента `/app`** (роли CO/Оп/Пг, 04 §2): Головна · Замовлення
(список / нове / повернення) · Товари (каталог / пакування / статистика) ·
Поставки · Фінанси (рахунки / операції / тарифи — постоплата) · Підтримка (чат) ·
Інтеграції · Команда · Налаштування.

**Складской контур `/warehouse`** (роли O/M): Черга збірки · Приймання
поставок · Інвентаризація · Повернення · Чати підтримки · Заявки клієнтів ·
Клієнти · Тарифи й комісії (O) · Звіти (O).

Правило: скрытый пункт меню — не защита; каждый роут проверяет роль +
`AccountScope`/`StaffScope` на сервере (04 §2). Референсное плоское меню из
десятка пунктов сознательно сгруппировано — это ответ на его перегруженность.

## 2. Архитектура-конструктор

Требование: меню, панели и настройки видоизменяются как детали конструктора —
добавить, убрать, поменять без переписывания кода и ломания архитектуры.
Реализация — три реестра; всё типизировано, «конфиг» — это код с zod-схемами,
а не свободный JSON.

**2.1 Реестр модулей.** Каждый раздел — модуль с манифестом: `id`, украинская
подпись, иконка, роут, требуемая роль/право (ссылка на матрицу 04 §3),
feature-флаг. Навигация обоих layout рендерится из реестра: добавить/убрать/
переставить раздел — одна запись; папка роута (App Router) живёт рядом,
«один модуль = одна папка + одна запись». Проверка прав в самом роуте остаётся
обязательной — реестр управляет только видимостью.

**2.2 Реестр виджетов дашбордов.** Виджет: `id`, роли, размер, data-loader
(server component), feature-флаг. Дашборд клиента (04 §4.2.1) и «Звіти»
владельца (04 §4.3.10) — контейнеры, рендерящие свой список виджетов из
реестра. Новый KPI — компонент + запись, контейнер не меняется.

**2.3 Настройки как данные.** `SettingDefinition` в коде: `key`, scope
(`PLATFORM | ACCOUNT | USER`), zod-тип значения, дефолт, украинская подпись,
группа, кто может менять (роль). Значения — таблица `Setting` (05 §D). Экраны
«Налаштування» обоих контуров рендерятся из дефиниций автоматически по группам
и типам полей: новая настройка = одна дефиниция, без миграции и без правки
экрана. Сюда же feature-флаги (scope PLATFORM).

Первые обитатели: расписание дайджеста низких остатков (#51) · дежурный
менеджер (#54) · пороги «дні без руху» дефолт (#52) · срок ответа клиента
по возврату (04 §3.4).

**2.4 Строчные модели в данных.** Там, где сущности множатся, расширение — данными,
не миграциями: строки тарифа (`TariffLine.serviceType` + `CUSTOM`), типы
доп. услуг, состав интеграций (карточки из реестра модулей).

**Граница честно:** это config-driven модульность, а не no-code билдер страниц.
Drag-n-drop конструктор интерфейсов не строим — несоразмерный объём и чужой
класс задач. «Легко менять» дают реестры и дисциплина одной записи.

## 3. Базовые UI-паттерны

Один компонент на паттерн; экраны собираются из паттернов, а не рисуются заново.

- **«Раздел-таблица»** (все списки): заголовок + счётчик · primary CTA справа ·
  статус-чипы с количеством (мультивыбор) · фильтры сеткой, сверх шести —
  «Ще фільтри» · таблица с меню строки «⋯» (не россыпь кнопок) · «Експорт в
  Excel» · пагинация; фильтры живут в URL — срез можно переслать ссылкой.
- **«Двухколоночная форма»** (замовлення, поставка): слева карточки блоков в
  порядке заполнения, справа sticky-панель состава с чузером товаров и итогом;
  submit дублируется сверху и снизу.
- **Setup-блокеры:** если действию не хватает предусловия (нет ФОП с ключом НП,
  нет товаров) — форма не «падает валидацией», а показывает блокер с кнопкой
  «исправить» (ссылка в нужный раздел). Список блокеров — чеклист онбординга.
- **Чеклист онбординга** на дашборде (04 §4.2.1) — компонент с прогрессом,
  а не текстовая модалка референса.
- **Сканер-паттерн** (збірка, приймання, інвентаризація, повернення):
  tablet-first, гигантский автофокус-инпут, звук+цвет на успех/ошибку/дубль,
  крупные кнопки действий, таймер и приоритет цветом (пороги 04 §6). Кнопка
  сканера закладывается в макет сразу, активируется позже (транскрипт).
- **Статусные бейджи** — только из токенов статусов (§4); один статус — один
  цвет во всех экранах.
- **Пустые состояния** всегда объясняют причину и дают действие: «Замовлень
  немає → Створити замовлення / Підключити інтеграцію»; фильтр без результата →
  «Скинути фільтри».
- **Опасные действия** — только в меню «⋯», с подтверждением и предупреждением
  о зависимостях («товар в архів: у ньому 3 активні замовлення»); где возможно —
  мягкое удаление/архив.
- **Финансовая прозрачность:** каждая операция в «Фінансах» раскрывается в
  деталку с deep-link на объект, строкой тарифа и формулой (04 §7).
- **Доступность:** label всегда (placeholder — не label), видимый фокус,
  клавиатурный путь по формам, контраст токенов проверяется при выборе палитры.

**Инвентарь состояний контрола — норма Definition of Done UI-задачи.** Каждый
интерактивный элемент обязан определить: default · hover · focus · loading
(повторный клик заблокирован) · success · error (конкретная причина) · disabled
с объяснением · permission-blocked (роль не позволяет — говорим об этом, а не
прячем молча) · empty-context (нет данных для действия).

Каждый список: initial loading (skeleton) · loaded · empty default (CTA) ·
empty filtered (сброс) · partial error (страница живёт) · full error (retry).
PR, добавляющий экран без этих состояний, не проходит ревью — это и есть
перенятый у аудита референса чек-лист качества.

## 4. Дизайн-система

- **Язык:** украинский, единственный на старте; терминология — глоссарий 04 §1;
  калька («аккаунт», «Колл центр») не допускается.
- **Свой визуальный язык, не клон референса:** светлая тема; дизайн-токены в
  одном файле (цвета статусов и семантики, spacing, radius, типографика);
  компоненты используют только токены.
- **Стек:** Tailwind CSS + shadcn/ui (Radix) поверх Next.js 16 / React 19.
  Server components по умолчанию; `'use client'` — точечно (формы, сканер,
  таймеры, чат). Формы — zod-схема, одна на форму и API (AGENTS.md). Обе
  зависимости заводятся отдельным маленьким PR (правило нового пакета);
  решение — строкой в 02-architecture тем же PR.
- **Живые элементы:** SLA-таймеры и очередь — периодический refresh серверных
  данных (интервал — настройка PLATFORM); чат — поллинг в MVP, real-time
  транспорт — после (решение при реализации, вместе с воркером #36).
- **Печать:** этикетка ТТН и документы — отдельные print-роуты без layout.
- Опция до кода: ключевые экраны (Головна, Черга збірки, Створення замовлення)
  прогнать макетами в Figma для согласования с заказчиком — решают люди.

## 5. Порядок реализации UI

Фазы после мержа документов; распределение по людям — `docs/07-workplan.md`.

- **A. Каркас интерфейса:** токены · базовые компоненты (Button, Input, Select,
  Table, Badge, Card, Dialog, Toast) · реестр модулей + реестр виджетов +
  settings-движок (§2) · два layout · **аутентификация целиком** (вхід /
  реєстрація / відновлення / підтвердження + машина онбординга, 04 §4.1, §8).
- **B. Кабинет клиента:** дашборд с чеклистом → товари (комплекты, пакування) →
  поставки → замовлення (список + створення, DRAFT) → повернення → фінанси
  (рахунки, операції) → чат підтримки → команда/налаштування.
- **C. Складской контур:** заявки клієнтів → приймання (замер объёма) → черга
  збірки з SLA → екран збірки → повернення → інвентаризація → чати підтримки →
  тарифи й комісії → звіти.
- Порядок внутри фаз — зависимостями данных: без товаров нет поставок, без
  поставок нет остатков, без остатков нет заказов.

## 6. Что переносим из аудита референса и что чиним

| Референс делает | Мы делаем |
|---|---|
| Онбординг — текстовая модалка | Чеклист с прогрессом и кнопками (§3) |
| Плоское меню 10+ пунктов | Группировка двух контуров (§1) |
| Удаление рядом с обычными действиями | Опасное — в «⋯» с подтверждением |
| Placeholder вместо label | Label всегда |
| Русский дефолт интерфейса | Украинский, единственный |
| Пассивные empty states («Замовлень немає») | Причина + действие |
| Facebook-виджет на дашборде | Только рабочие виджеты из реестра |
| Баланс с «поповнити» | Постоплата: рахунки и прозрачные операции (#55 ↷) |
| Секундомер отдельной страницей | SLA-таймеры прямо в очереди и задаче |
