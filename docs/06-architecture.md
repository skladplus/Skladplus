## Принятые риски

Это решения, а не упущения.

1. **Автодеплой из `main` без человеческого гейта.** Зелёный CI не защищает от автора, который пишет и код, и тесты. Страховка — CodeRabbit и откат за 30 минут.
2. **PR, правящий `.github/`, проверяется уже изменённым workflow** — гейт проверяет сам себя. Реализуется только при компрометации аккаунта одного из двоих.
3. **Bus factor за пределами организации не закрыт:** нет офлайн recovery-кодов, второго админа в Neon, Vercel и Sentry, зеркала репозитория. Два владельца организации закрывают главный сценарий, остальные остаются.
4. **Без карантина на свежие npm-релизы.** Барьер — только `--ignore-scripts` в CI.
5. **Публичный репозиторий с тарифами заказчика.**
6. **Deny-правила агентов — не граница, а трение.** Запрет `curl` обходится через `node -e`; запрет чтения `.env` — через `cat` и `grep -r`. Реально работает вынос секретов за пределы рабочей папки, всё остальное лишь удорожает случайную ошибку.
7. **`AccountScope` обходится прямым вызовом `unsafePrisma()`.** Примитив убирает случайную ошибку и держит доступ в одном месте, но обход не запрещён: проверки CI на прямой Prisma в `apps/` нет. До неё это снижение риска, а не гарантия изоляции клиентов.

## Где план разошёлся с реальностью: организация и приложение

Найдено при переносе в организацию и постройке приложения.

| Что | Как оказалось |
|---|---|
| Перенос репозитория в организацию | **Сбросил secret scanning и push protection в `disabled`.** На личном репозитории они были включены; Free-организация ставит их выключенными по умолчанию для входящих репозиториев. Возвращено вручную, плюс выставлены org-настройки по умолчанию, чтобы следующий репозиторий не наступил на то же |
| Проверка `codeowners/errors` | Эндпоинту нужен **полный ref**: `?ref=refs/heads/main` отдаёт `{"errors":[]}`, а без него и с `?ref=main` — 404. Файл валиден |
| CODEOWNERS как «авто-запрос ревью» | Не работает. События `review_requested` не возникает: авто-запрос включается правилом `require_code_owner_review`, а оно делает апрув обязательным — то есть создаёт очередь, от которой отказались. | Снятие scope `gist` | Невозможно: `gh auth refresh --remove-scopes` сообщает, что `repo`, `read:org` и `gist` — минимальный набор gh CLI. Снят только `delete_repo`. Остаётся deny-правило `Bash(gh gist:*)` у агента — это трение, а не граница |
| Организация создаётся через API | Нельзя: `POST /admin/organizations` есть только в GitHub Enterprise. Создано через веб; scope `admin:org` нужен не для создания, а для приглашений и проверок после |
| Порт локального Postgres | 5432 занят базой другого проекта на той же машине. Skladplus слушает **5433**, переопределяется `SKLADPLUS_DB_PORT` |
| Prisma 7: `url` и `directUrl` в схеме | Удалены из схемы, переехали в `prisma.config.ts`; рантайм получает driver adapter (`@prisma/adapter-pg`). Замысел плана сохранён: миграции ходят только по прямому подключению |
| Строгий `env()` из `prisma/config` | Роняет **любую** команду при отсутствии переменной, включая `prisma generate` на сборке Vercel, где `SHADOW_DATABASE_URL` нет и быть не должно. Используется `process.env` |

| Генерация клиента Prisma в CI | Клиент не коммитится, поэтому нужен **каждому** джобу, а не только сборке. Первый прогон уронил `typecheck` и `unit`; локально они проходили на клиенте от прошлых запусков — ровно тот случай, когда зелёное локально ничего не значит. | Плагины пинуются по `gitCommitSha` | Не сделано осознанно. Пин официального маркетплейса Anthropic заморозил бы и обновления безопасности всех 286 плагинов, а механизма их отслеживания, вроде Dependabot, нет. Решение пересмотреть, если появится сторонний маркетплейс с плагинами в работе |

### Override на `deepmerge-ts`

Dependabot нашёл HIGH в `deepmerge-ts@7.1.5` — исчерпание стека при слиянии
рекурсивных объектов. Пакет приходит транзитивно из `@prisma/config@7.9.1`,
и версии Prisma без него нет: 7.9.1 — последняя.

Практический риск для нас околонулевой: `@prisma/config` сливает наш собственный
конфиг, который не приходит извне и рекурсивным быть не может. Но висящий HIGH
приучает не смотреть на алерты, поэтому поднят через `pnpm.overrides` до 8.0.2.

Мажорный апгрейд транзитивной зависимости — риск сам по себе, поэтому проверен
весь конвейер, а не только сборка: `generate`, `deploy`, `status`, `diff` (включая
ненулевой код при дрейфе), типы, тесты, сборка. Override снимается, когда Prisma
подтянет восьмёрку сама.

### Postgres 18

Локально, в CI и на Neon — одна мажорная версия. Расхождение здесь даёт зелёные
тесты при красном проде, как и расхождение часовых поясов. Выбрана 18, а не 17:
горизонт поддержки длиннее, а день ноль — последний момент, когда смена мажора
ничего не стоит.

При переходе всплыло: **образ `postgres:18` сменил точку монтирования.** Том
вешается на `/var/lib/postgresql`, а не на `/var/lib/postgresql/data` — данные
раскладываются по версионным подкаталогам, чтобы работал `pg_upgrade --link`.
Со старой точкой контейнер уходит в цикл перезапуска, и это не видно из
`docker compose up`: нужен `docker logs`. В CI сервис-контейнер тома не имеет,
поэтому там проблема не проявилась бы — она ждала бы разработчика на его машине.

## Neon: как заведён и почему так

Проект `Skladplus`, `aws-eu-central-1` (Франкфурт — регионов ближе к Украине
у Neon нет), Postgres 18, тариф Launch. Launch выбран потому, что он больше
не стоит фиксированных денег: чистый pay-as-you-go без базовой платы, при нашей
нагрузке $3–5 в месяц. За это — окно восстановления 7 дней вместо 6 часов
на Free и защищённые ветки.

**Поправлено после создания:** ветка `production` переведена в protected
(создаётся незащищённой), автоскейл снижен с 8 CU до 1 — и в настройках
по умолчанию, и на уже созданном эндпоинте, потому что первое действует
только на новые.

### Границы доступа агента

План требовал «Neon MCP видит только ветку с синтетикой». **Такой границы
в Neon не существует:** ключи бывают персональные, организационные
и project-scoped; ветка областью действия быть не может.

Это важнее, чем кажется, потому что боевая база другого клиента (NovaPostBot)
лежит **в той же организации Neon**. OAuth-авторизация MCP — кнопка
«Authenticate» в `/mcp` — выдаёт доступ ко всему аккаунту, то есть к его проду.
Онбординг Neon вдобавок сам прописал такой сервер в user-scope, где он
действовал бы во всех проектах машины; он удалён.

Работающая граница — **project-scoped ключ**. Проверено с трёх сторон:
свой проект открывается, чужой отдаёт `project not found`, список проектов
организации — `not allowed to perform actions outside the project this key
is scoped to`.

Ключ хранится только в `~/.skladplus/env` (0600). В конфиг MCP записана
переменная `${NEON_API_KEY}`, не значение. Пока в базе синтетика, проекта
как границы достаточно; перед первым боевым клиентом — пункт 45
в `docs/09-findings-backlog.md`.

При выпуске ключа первая попытка напечатала его в вывод команды. Ключ
немедленно отозван и выпущен заново, вывод второй попытки в терминал
не попадает. Записано здесь, потому что «секрет мелькнул в логе» —
это скомпрометированный секрет, а не досадная мелочь.

### Мастер `neon init --agent` не применялся

Он выдаёт агенту инструкции, которые ломают четыре наших решения:
`npm install` в pnpm-воркспейсе, установка пакетов через `npx -y` (запрещено
как неповторяемая сборка), `neon env pull` со строкой подключения в файл
внутри репозитория (секреты живут вне рабочей папки) и `@neondatabase/serverless`
вторым путём доступа к базе мимо `@prisma/adapter-pg`. Завершается он
установкой Neon Auth — архитектурным решением, которого нет в плане.

Инструкции прочитаны в песочнице как данные и не выполнены. Правило про
такие мастера добавлено в `AGENTS.md`: Codex получит от Neon ровно тот же текст.

### Строки подключения к Neon локально не хранятся

Локальная разработка идёт на Postgres из compose. Прод и preview получают
строки от нативной интеграции Neon↔Vercel, которая заводит ветку БД на каждый
PR и пишет переменные сама. Проставленные руками потом конфликтуют с её
значениями, поэтому интеграция ставится **до** первого preview-деплоя.

## Границы доступа агентов к внешним сервисам

Общее правило: **MCP подключается только там, где доступ можно ограничить.**
Где ограничить нельзя — сервис используется через CLI с узким токеном либо
через дашборд руками.

| Сервис | Решение |
|---|---|
| **Neon** | Подключён. Ключ ограничен проектом Skladplus. Проверено: свой проект открыт, `list_projects` отдаёт `not allowed for organization API keys`, чужой проект недоступен |
| **Vercel** | **Не подключаем.** Документация Vercel прямо говорит: подключение MCP выдаёт агенту тот же доступ, что у учётной записи пользователя. Ограничения по проекту или команде нет, OAuth без альтернативы. Настройка — через дашборд, остальное — `vercel` CLI с токеном, ограниченным командой |
| **Sentry** | Не подключаем на этапе 0: проекта в Sentry ещё нет, а токен читает ошибки по всему аккаунту |
| **Prisma-Remote** | Не подключаем: он про Prisma Postgres, которым мы не пользуемся. Локальный `Prisma-Local` работает и достаточен |
| **GitHub** | Не подключаем: MCP требует подписки Copilot, а `gh` CLI закрывает всё то же самое и уже используется |
| **context7, playwright, semgrep** | Подключены: доступа к нашим данным не имеют |

Отдельно: `desktop-commander` из user-scope запускается как `npx -y ...@latest`,
то есть тянет свежий пакет при каждом старте и даёт широкий доступ к файловой
системе и терминалу. Это тот же запрещённый паттерн, что `pnpm dlx`, и открытый
вход для supply-chain. К Skladplus отношения не имеет и подлежит удалению.

## Vercel: сборка монорепо

Настройки сборки живут в `apps/web/vercel.json`, а не только в дашборде:
`vercel.json` перекрывает настройки проекта, версионируется и виден второму
разработчику. В дашборде остаётся то, что оттуда задать нельзя: Root Directory,
переключатель «Include source files outside of the Root Directory» и переменные
окружения.

Команда сборки обязана начинаться с генерации клиента Prisma. Клиент
не коммитится, а `next build` его не создаёт — на Vercel это даёт ту же ошибку
`Cannot find module './generated/client'`, что уронила первый прогон CI.
Форма `pnpm --filter @skladplus/db db:generate` выбрана потому, что бинарь
`prisma` лежит в зависимостях `packages/db`, а не `apps/web`: при изолированных
`node_modules` pnpm прямой вызов `prisma` из `apps/web` не разрешается.

Отдельно про кэш: при попадании в кэш сборки Vercel пропускает установку
зависимостей, поэтому генерация обязана быть шагом сборки, а не постустановочным
скриптом — иначе на прод уедет устаревший клиент.

## Vercel после подключения интеграции Neon

Проверено через API, а не по экрану настроек.

| Что | Было | Стало |
|---|---|---|
| Регион функций | `iad1` — Вашингтон | `fra1` — Франкфурт |
| Имя прямого подключения | ждали `DIRECT_URL` | интеграция даёт `DATABASE_URL_UNPOOLED` |

**Регион — не косметика.** База в `aws-eu-central-1`, а функции по умолчанию
поднялись в Вашингтоне: каждый запрос Prisma ходил бы через Атлантику, и это
попало бы прямо в SLA «30 рабочих минут» — только заметили бы не сразу,
а на живых заказах.

**Имя переменной** подстраиваем мы, а не интеграция. Она перезаписывает свои
значения при каждом деплое, поэтому ручное переименование не переживёт первый
же пуш. `prisma.config.ts` принимает оба имени: локально и в CI — `DIRECT_URL`,
на Vercel — `DATABASE_URL_UNPOOLED`.

Подтверждено также: `sourceFilesOutsideRootDirectory: true` (иначе pnpm-воркспейс
не собрался бы), `nodeVersion: 24.x` совпадает с `.nvmrc`, `gitForkProtection`
и `protectedSourcemaps` включены, проект непубличный — логи сборки посторонним
не видны.

## Миграции прода

Проверка после первого успешного деплоя показала: боевая ветка Neon **пуста —
ни одной таблицы, включая `_prisma_migrations`**. Миграции туда никогда
не применялись. Джоб `db` в CI гоняет их против сервис-контейнера, а не против
Neon, и этого достаточно для проверки конвейера, но не для прода.

Пока единственная миграция пустая, это безвредно. Опасно другое: механизма
не было вовсе, и первая же настоящая миграция не доехала бы до прода молча —
приложение пошло бы работать против схемы, которой нет.

Заведён отдельный workflow `migrate.yml` на `push: main`:

- `concurrency: deploy-main` с `cancel-in-progress: false`. Прерывать миграцию
  на полпути нельзя: база останется в промежуточном состоянии, а
  `_prisma_migrations` запомнит её незавершённой.
- Отдельно от сборки Vercel: та параллельна и кэшируется, из-за чего две миграции
  могли бы поехать на одну базу.
- Явная проверка, что секрет задан: без неё пустая переменная дала бы
  «нечего применять» и зелёный прогон при неприменённых миграциях.
- `migrate status` до и после — в логе видно, что именно поехало.

Строка подключения лежит в секрете репозитория `NEON_PRODUCTION_DIRECT_URL`,
прямая (без `-pooler`): pooled-соединение миграции не переживёт. Репозиторий
публичный, но секреты недоступны PR из форков, а `push` в `main` закрыт
ruleset'ом.

**Незакрытое:** миграция и деплой кода идут параллельно, поэтому новый код может
доехать раньше своей миграции. Пока схема пуста, это не проявляется; лечится
дисциплиной expand/contract — пункт 37 в `docs/09-findings-backlog.md`.

## Обход защиты деплоев для автоматизации

Vercel Authentication включена: и preview, и production отдают 302 всем,
кроме авторизованных участников команды.

Побочный эффект: проверить `/api/health` снаружи нельзя, и Playwright не сможет
гонять тесты против preview (issue #12). Для этого у Vercel есть штатный
механизм — Protection Bypass for Automation: запрос с заголовком
`x-vercel-protection-bypass: <секрет>` проходит мимо защиты.

Секрет включён и лежит **только** в `~/.skladplus/env` под именем
`VERCEL_AUTOMATION_BYPASS_SECRET`. В репозиторий он не попадает. Для CI его
нужно будет положить в секреты репозитория, когда появится e2e-джоб против
preview.

Проверка прода командой:

```bash
set -a; . ~/.skladplus/env; set +a
node -e 'fetch("https://<деплой>.vercel.app/api/health",{redirect:"manual",headers:{"x-vercel-protection-bypass":process.env.VERCEL_AUTOMATION_BYPASS_SECRET}}).then(async r=>{if(!r.ok){console.error("HTTP "+r.status);process.exitCode=1;return}console.log(await r.text())}).catch(e=>{console.error(e);process.exitCode=1})'
```

`redirect:"manual"` и проверка статуса здесь не украшение: без них неверный
секрет уводит запрос на страницу входа Vercel, команда печатает её HTML и
выходит с нулём — ложный успех ровно там, где проверяют обход защиты.

**Это секрет ровно той же силы, что пароль от деплоя:** кто им владеет, тот
видит preview и production в обход авторизации. Хранится как остальные —
вне рабочей папки, права 0600. Отзывается и перевыпускается в настройках
проекта на Vercel.

### CodeRabbit: установки GitHub App недостаточно

Приложение `coderabbitai` установлено в организацию с доступом ко всем
репозиториям — это видно через `gh api orgs/skladplus/installations`. Но ревью
не появлялось ни на одном PR, и прямой вызов `@coderabbitai review` тоже остался
без ответа. У CodeRabbit собственный тумблер на репозиторий в его дашборде,
и без него сервис за репозиторием не следит.

Проверять надо не установку приложения, а факт ревью на живом PR: установка
выглядит как «готово» и ничего не делает.

Отсюда же правило в `AGENTS.md`: PR не мержится раньше, чем ответил CodeRabbit.
Все PR этапа 0 мержились через минуту после открытия — ревью не успело бы,
даже будь оно включено.
