# 02 — Решения

Единый журнал: решение · обоснование · дата. Отвергнутые варианты записаны вместе
с принятыми — иначе через месяц их начнут пересматривать по кругу.
ADR отдельными файлами не ведём: при двух разработчиках один список читается быстрее.

## Процесс

| Решение | Обоснование | Дата |
|---|---|---|
| Апрув второго человека на merge не обязателен | Двое, работают параллельно; обязательный апрув превратился бы в очередь. Гейт — зелёный `ci-ok` и CodeRabbit | 2026-08-22 |
| Прямой push в `main` закрыт для всех, `bypass_actors: []` | Исключение для владельца обесценивает защиту: обходить будут в спешке, а спешка и есть источник сломанного `main` | 2026-08-22 |
| Только squash-merge | Линейная история; merge-коммиты и rebase отключены на уровне репозитория, а не договорённости | 2026-08-22 |
| `squash_merge_commit_message = BLANK` | При PR из одного коммита GitHub предзаполняет тело PR телом коммита — запрещённый AI-трейлер вернулся бы этим путём | 2026-08-22 |
| `strict_required_status_checks_policy: false` | При двух параллельных писателях strict сериализует мержи: каждый чужой merge сбрасывает готовность второго. Вместо него `allow_auto_merge` | 2026-08-22 |
| Один обязательный чек — агрегат `ci-ok` | Иначе новый job не станет обязательным автоматически, а переименование старого молча откроет мерж | 2026-08-22 |
| `paths:` и `paths-ignore:` в CI запрещены | Отфильтрованный обязательный чек навсегда остаётся `pending` и блокирует PR | 2026-08-22 |
| Отвергнут commitlint | Conventional Commits соблюдаются двумя людьми без робота; ещё один красный чек не окупается | 2026-08-22 |
| AI в авторстве запрещён | Требование заказчика работ: контрибьюторы — только люди. Механизм: `includeCoAuthoredBy: false` + правило в `AGENTS.md` для Codex + job `authorship` как страховка. `git config` этим не управляет — трейлер добавляет агент, а не git | 2026-08-22 |
| Каркас делает один человек, не оба | День-полтора работы; координация двоих съела бы больше, чем сэкономила | 2026-08-22 |
| После каркаса — trunk-based, ветки на часы, stacked PR, флаги, worktrees | Узкое место при работе с агентами — не написание кода, а ревью и интеграция. Выигрыш даёт сокращение времени жизни ветки, а не рост их числа | 2026-08-22 |
| Домен делится по ограниченным контекстам | Товары/поставки/остатки одному, заказы/отправки/возвраты другому, каждый от таблицы до экрана. Деление по слоям заставляло бы ждать друг друга | 2026-08-22 |

## Принятые риски

Это решения, а не упущения.

1. **Автодеплой из `main` без человеческого гейта.** Зелёный CI не защищает от автора, который пишет и код, и тесты. Страховка — CodeRabbit и откат за 30 минут.
2. **PR, правящий `.github/`, проверяется уже изменённым workflow** — гейт проверяет сам себя. Реализуется только при компрометации аккаунта одного из двоих.
3. **Bus factor за пределами организации не закрыт:** нет офлайн recovery-кодов, второго админа в Neon, Vercel и Sentry, зеркала репозитория. Два владельца организации закрывают главный сценарий, остальные остаются.
4. **Без карантина на свежие npm-релизы.** Барьер — только `--ignore-scripts` в CI.
5. **Публичный репозиторий с тарифами заказчика.**
6. **Deny-правила агентов — не граница, а трение.** Запрет `curl` обходится через `node -e`; запрет чтения `.env` — через `cat` и `grep -r`. Реально работает вынос секретов за пределы рабочей папки, всё остальное лишь удорожает случайную ошибку.

### Новый принятый риск

7. **Второй владелец организации без двухфакторной аутентификации.** У `@Stepandj`
   2FA выключена, а прав у него столько же, сколько у первого владельца: он может
   снять ruleset, выключить push protection и вычистить организацию. Требование 2FA
   на уровне организации не включено намеренно — оно немедленно исключило бы его
   из организации. Это самое слабое место всей защиты: ruleset, `bypass_actors: []`
   и push protection обходятся тем, кто владеет учётной записью.

### Override на `deepmerge-ts` (2026-08-22)

Dependabot нашёл HIGH в `deepmerge-ts@7.1.5` — исчерпание стека при слиянии
рекурсивных объектов. Пакет приходит транзитивно из `@prisma/config@7.9.1`,
и версии Prisma без него нет: 7.9.1 — последняя.

Практический риск для нас околонулевой: `@prisma/config` сливает наш собственный
конфиг, который не приходит извне и рекурсивным быть не может. Но висящий HIGH
приучает не смотреть на алерты, поэтому поднят через `pnpm.overrides` до 8.0.2.

Мажорный апгрейд транзитивной зависимости — риск сам по себе, поэтому проверен
весь конвейер, а не только сборка: `generate`, `deploy`, `status`, `diff` (включая
ненулевой код при дрейфе), типы, тесты, сборка. Override снимается, когда Prisma
подтянет восьмёрку сама.

### Postgres 18 (2026-08-22)

Локально, в CI и на Neon — одна мажорная версия. Расхождение здесь даёт зелёные
тесты при красном проде, как и расхождение часовых поясов. Выбрана 18, а не 17:
горизонт поддержки длиннее, а день ноль — последний момент, когда смена мажора
ничего не стоит.

При переходе всплыло: **образ `postgres:18` сменил точку монтирования.** Том
вешается на `/var/lib/postgresql`, а не на `/var/lib/postgresql/data` — данные
раскладываются по версионным подкаталогам, чтобы работал `pg_upgrade --link`.
Со старой точкой контейнер уходит в цикл перезапуска, и это не видно из
`docker compose up`: нужен `docker logs`. В CI сервис-контейнер тома не имеет,
поэтому там проблема не проявилась бы — она ждала бы разработчика на его машине.
