# 02 — Продуктовая спецификация: кабинет клиента и складской контур

Полная редакция: разделы заполнены. Документ — источник истины для матриц прав,
карточек экранов и машин статусов; правится тем же PR, что меняет поведение.

Источники: транскрипт видео-прохода заказчика от 2026-08-22 и словесный разбор
структуры референсной системы (сами материалы — вне git, правило №3 `AGENTS.md`);
ответы опросника и отложенное — `docs/09-findings-backlog.md`, принятые
решения — `docs/06-architecture.md`. `#N` — номер пункта бэклога, ссылка
на GitHub идёт со словом (`PR #23`, `issue #16`).

Документ фиксирует продуктовое поведение; визуальный дизайн не фиксирует
(это `docs/03-ux-ui.md`), схему данных не фиксирует (`docs/04-domain-draft.md`).

## 0. Как читать документ

Три формата описания, каждый с обязательными полями:

1. **Карточка экрана**: Назначение (одна фраза) · Кто видит (роли из §2) ·
   Блоки сверху вниз (нумерованный список в порядке макета) · Действия (глагол →
   что происходит) · Фильтры и статусы · ⚠ Открытое (только номером `#NN`).
2. **Матрица «роль × действие»**: строки — действия домена, колонки — роли;
   `✓` — разрешено · `○` — разрешено с ограничением (сноска) · `—` — запрещено.
   Матрица — источник истины для проверок прав в коде; скрытие кнопки без
   проверки на сервере не считается реализацией строки.
3. **Машина статусов**: таблица «статус UA · enum · кто переводит · триггер ·
   эффекты (резерв / деньги / SLA / уведомления)». Любой переход, которого нет
   в таблице, в системе невозможен.

## 2. Роли и границы данных

| Роль (код) | Кто это | Граница данных | Контур |
|---|---|---|---|
| `owner` | владелец склада (заказчик) | все account'ы | складской + всё из manager |
| `manager` | менеджер склада: сборка, приёмка, возвраты, инвентаризация, онбординг клиентов, чат поддержки | все account'ы | складской |
| `client_owner` | владелец клиента-магазина | один account | кабинет клиента, всё |
| `client_member` | сотрудник команды клиента | один account | кабинет клиента по пресету |

Пресеты `client_member` (#65): **Власник** — как `client_owner` ·
**Оператор** — всё, кроме «Фінанси», «Команда», «Налаштування» ·
**Перегляд** — только чтение всех разделов, кроме «Фінанси».

Правила, действующие поверх любой матрицы ниже:

- Данные клиента открываются только через `forAccount(accountId)`
  (`packages/db/src/scope.ts`); чужое — 404, не 403.
- Персонал (`owner`, `manager`) работает через второй примитив `StaffScope`:
  кросс-аккаунтные списки (очередь сборки, заявки) — по роли персонала,
  а конкретный объект клиента открывается затем через `forAccount(order.accountId)`.
- Разработчики — не роль в БД (#21): доступ к инфраструктуре, не к кабинету.
- Ролей «збірник» / «керівник збірки» не существует (#21): сборку ведут менеджеры.

## 4. Карта экранов

### 4.1 Контур аутентификации

Общее для контура: язык — украинский; у полей — label, не placeholder; ошибки
inline; rate limiting и остальные правила безопасности — §8.

#### 4.1.1 «Вхід»

**Назначение.** Вход по email и паролю. **Кто видит.** Неавторизованные.

**Блоки.** 1. Логотип и заголовок «Вхід до кабінету». 2. Email · Пароль
(показать/скрыть) · чекбокс «Запам'ятати мене». 3. Кнопка «Увійти» (loading-
состояние, повторный клик заблокирован). 4. Ссылки: «Забули пароль?» →
§4.1.3 (у референсной системы этой кнопки нет — у нас обязательна) ·
«Створити акаунт» → §4.1.2.

**Действия.** «Увійти»: при успехе — по роли: персонал → складской контур,
клиент → кабинет (или экран статуса заявки, если не ACTIVE §5.4). Ошибка всегда
одна: «Невірний email або пароль» — без уточнения, что именно неверно.

#### 4.1.2 «Реєстрація»

**Назначение.** Саморегистрация клиента → заявка на подключение (#14).
**Кто видит.** Неавторизованные.

**Блоки.** 1. Назва магазину · Email · Телефон · Пароль (индикатор силы, ≥ 12).
2. Чекбокс согласия с публичным договором и политикой конфиденциальности
(ссылки). 3. Кнопка «Створити акаунт». 4. Ссылка «Вже є акаунт? Увійти».

**Действия.** «Створити акаунт» → аккаунт в NEW → письмо подтверждения →
§4.1.4. Если email занят — на экране тот же успех («перевірте пошту»), а в
письме — «у вас уже есть аккаунт, войдите»: существование email не раскрывается.

#### 4.1.3 «Відновлення пароля»

**Назначение.** Сброс пароля по email. **Кто видит.** Неавторизованные.

**Блоки.** Шаг 1: Email → «Надіслати лист»; ответ всегда «Якщо email
зареєстровано — ми надіслали посилання». Шаг 2 (по ссылке из письма, токен
одноразовый, TTL ≤ 1 ч): Новий пароль · Повторіть пароль → «Змінити пароль».

**Действия.** Успешная смена завершает все активные сессии пользователя и ведёт
на «Вхід» с сообщением. Просроченный/использованный токен — экран «посилання
не діє» с кнопкой запросить новое.

#### 4.1.4 «Підтвердження контакту»

**Назначение.** Состояние CONTACT_PENDING (§5.4): просьба подтвердить email.
**Кто видит.** Авторизованный пользователь неподтверждённого аккаунта.

**Блоки.** 1. «Підтвердіть email: лист надіслано на …». 2. «Надіслати ще раз»
(не чаще раза в минуту). 3. После подтверждения — экран «Заявку передано
менеджеру» со статусом заявки (MANAGER_REVIEW / NEEDS_CHANGES с комментарием
менеджера и формой правок).

### 4.2 Кабинет клиента

#### 4.2.1 «Головна» (дашборд)

**Назначение.** Операционный центр клиента: всё, что требует внимания, и
быстрый вход в частые действия. **Кто видит.** CO, Оп, Пг (все виджеты, кроме
финансовых — их видит только CO; состав — реестром виджетов,
`docs/03-ux-ui.md`).

**Блоки сверху вниз.**

1. **Быстрые действия** (4): «Створити замовлення» → §4.2.3 · «Створити
   поставку» → §4.2.7 · «Фінанси» → §4.2.9 (вместо «поповнити баланс» из
   видео — постоплата, §9) · «Підтримка» → §4.2.10.
2. **Чеклист онбординга** (пока не завершён, вместо приветственной модалки):
   налаштування профілю → ФОП і ключ НП → перший товар → перша поставка →
   перше замовлення; каждый шаг — кнопкой, прогресс виден, выполненные
   сворачиваются.
3. **«Потребує уваги»** — 4 счётчика-ссылки: «В обробці понад 30 хв» (журнал
   событий §5.1) · «Низький залишок» (#51) · «Помилки в замовленнях» (#57) ·
   «Повернення: очікують рішення» (§5.2).
4. **KPI-карты**: Замовлення сьогодні (и порівняння зі вчора) · Відправлено
   сьогодні (и порівняння) · Замовлення в роботі (+«переглянути») · Оборот
   місяця (и порівняння; только CO).
5. **Склад и деньги**: Зайнято м³ (+«показати історію» — таблица дат и объёмов,
   питает тариф #2) · Проблемні замовлення · Накладені платежі в дорозі
   (#53, кнопка «Оновити»).
6. **Динаміка замовлень** — график за 7/30 днів, клик → §4.2.8.
7. **Статуси замовлень** — количество по группам §5.1.
8. **Товари, що закінчуються** — топ ниже порога, «перейти до залишків».
9. **Останні замовлення** — 5 строк: номер · клієнт-канал · ТТН · статус · сума.

**⚠ Открытое.** #30 (какие срезы нужны владельцу — его дашборд в §4.3).

#### 4.2.2 «Замовлення» (список) — образец формата

**Назначение.** Рабочий список всех заказов клиента с фильтрами и историей.

**Кто видит.** CO, Оп, Пг (свой account); O, M — в складском контуре свой
экран очереди (§4.3.1), но могут открыть список любого клиента из карточки
клиента (§4.3.8).

**Блоки сверху вниз.**

1. Заголовок + счётчик найденного; справа — «Експорт в Excel», «Додати нове
   замовлення» (primary).
2. Статус-чипы с количеством по каждому статусу §5.1 (мультивыбор), свёрнутые
   «Показати ще…» после первых пяти.
3. Фильтры (сетка, «Ще фільтри» сверх шести): дата з/по · номер замовлення ·
   ID зовнішньої системи · номер ТТН · отримувач (ім'я або телефон) · спосіб
   оплати · платник доставки · сума від/до · канал (кабінет/CRM/вручну).
4. Таблица: номер · канал · дата створення · статус (бейдж) · отримувач ·
   кількість товарів · сума · ТТН · коментар; действия строки — меню «⋯».
5. Пагинация + размер страницы (20/50/100).

**Действия.** «Додати нове замовлення» → §4.2.3 · строка: відкрити деталку ·
копіювати замовлення (создаёт DRAFT с тем же составом) · друк ТТН · поставити
на паузу · скасувати (по матрице §3-обр) · «Показати проводку» (CO).

**Фильтры и статусы.** Статусы — §5.1 полностью; фильтры сохраняются в URL
(ссылку можно переслать коллеге — откроется тот же срез).

**Пустые состояния.** Нет заказов вообще → CTA «Створити замовлення» +
«Підключити інтеграцію»; фильтр без результата → «Скинути фільтри».

**⚠ Открытое.** #27 (платность отмены по стадиям), #35 (приоритет при пике).

#### 4.2.3 «Створення замовлення» — образец формата

**Назначение.** Ручное создание заказа менеджером клиента; тот же валидационный
контракт (zod) используется каналами CRM и API.

**Кто видит.** CO, Оп.

**Блоки сверху вниз** (двухколоночная форма, справа — sticky-панель товаров).

1. **ФОП відправника**: селект профилей ФОП клиента; последний использованный
   предзаполнен (из транскрипта); «Додати ФОП» → Налаштування. Без ФОП с ключом
   НП форма блокируется с объяснением и ссылкой (setup-blocker).
2. **Отримувач**: тип (фізична/юридична особа) · ім'я, по батькові, прізвище ·
   телефон · «Додати email» (опционально). Данные уходят в отдельную таблицу
   получателей (#18).
3. **Доставка**: способ (Нова Пошта — единственный на старте) · місто/відділення/
   поштомат (поиск по API НП) · адресна доставка отдельной строкой.
4. **Оплата**: повна оплата / передоплата / накладений платіж · сума замовлення
   (предзаполняется суммой товаров, можно править) · отримана передоплата →
   залишок считается автоматически, можно скорректировать · платник доставки ·
   платник зворотної доставки грошей · оголошена вартість.
5. **Додатково**: ID зовнішньої системи · коментар для збірки (необязательный).
6. **Товари** (правая панель): поиск по артикулу/назві → строки «фото · артикул ·
   назва · доступний залишок · ціна · кількість (±)»; комплект разворачивается
   в состав при сборке (#24); «віртуальний» товар добавляется при нулевом
   остатке с пометкой «не зі складу» (#50).
7. **Підсумок**: кількість товарів · сума · передоплата · залишок · оголошена
   вартість; кнопки «Створити замовлення» (→ NEW, резерв) · «Зберегти чернетку»
   (→ DRAFT, без резерва) · «Очистити форму».

**Действия и валидации.** «Створити» активна только при валидной форме.
Ограничение количества доступным остатком в поле — удобство, а не защита:
**резерв берётся сервером атомарно**, в одной транзакции с созданием заказа
(«уменьшить доступный остаток, если хватает, иначе отказ»); при гонке двух
заказов на последний остаток второй получает ошибку «залишок змінився» с
актуальным числом (#10, #23). Все прочие ошибки — inline у поля.

**⚠ Открытое.** #32 (частичная сборка), #26 (повторная отправка после невыкупа).

#### 4.2.4 «Повернення»

**Назначение.** Список проблемных отправлений и их разбор. **Кто видит.**
CO, Оп, Пг (по §3.4).

**Блоки.** 1. Заголовок; справа — «Зафіксувати повернення» (тип «після
вручення», #22). 2. Статус-чипы §5.2 + фильтр типа (відмова / після вручення).
3. Фильтры: дата з/по (дефолт — последние 10 дней) · номер повернення · номер
замовлення · ТТН · отримувач · ID зовнішньої системи. 4. Таблица: номер
повернення · номер замовлення · тип · дата · отримувач · ТТН · статус · сума ·
кількість. 5. Деталка возврата: состав, фото, состояние позиций, комментарии
(лента), связанный заказ, история статусов.

**Действия.** «Прийняти рішення» на статусе «Очікує рішення» (повернути на
склад / інше — по типу); комментарий; переход в заказ.

**⚠ Открытое.** #22 ↷ (цены по типам), #26 (повторная отправка после невыкупа).

#### 4.2.5 «Товари»

**Назначение.** Каталог SKU клиента и управление карточками. **Кто видит.**
CO, Оп, Пг (по §3.2).

**Блоки.** 1. Заголовок; справа: «Статистика товарів» → §4.2.8 · «Пакування» →
§4.2.6 · «Імпорт товарів» · «Експорт в Excel» · «Додати новий товар» (primary).
2. Фильтры: пошук (назва/артикул/штрих-код) · категорія · «є в наявності»
(тумблер) · розмір сторінки. 3. Таблица: фото · артикул · назва · категорія ·
бренд · штрих-код · фізичний залишок · доступний залишок (#23) · мін. залишок ·
ціна · статус (активний / низький залишок / немає в наявності / архів).

**Карточка товара** (создание/правка):

- поля: артикул (обов'язково) · назва (обов'язково) · категорія (создание
  «на льоту») · опис · бренд · до 2 штрих-кодів · фото (файл или ссылка) ·
  ціна · собівартість (видит только CO) · зовнішній ID · габарити (довжина ×
  ширина × висота; объём для тарифа фиксирует склад при приёмке, #58);
- тумблеры: «Це комплект» (+состав из товаров, #24) · «Віртуальний товар»
  (#50, с пояснением «продаж без залишку — збирається не зі складу») ·
  «Повідомляти про низький залишок» + порог (#51) · порог «дні без руху»
  (дефолт 30, #52);
- вкладки деталки: Загальна інформація · Історія рухів · Історія розміщень ·
  Списання.

**Импорт Excel**: xls/xlsx до 10 МБ; существующий артикул обновляется, новый
создаётся; обязательные колонки — артикул и назва; предпросмотр изменений до
применения; ошибки построчно.

**⚠ Открытое.** #33 (списание брака), #34 (хранение сверх срока).

#### 4.2.6 «Пакування»

**Назначение.** Учёт упаковки клиента как складской позиции (#60). **Кто
видит.** CO, Оп, Пг.

**Блоки.** 1. «Створити нове пакування» · «Статистика пакування» · пошук.
2. Таблица: фото · артикул · назва · залишок · ціна. 3. Карточка: назва
(обов'язково) · артикул · штрих-код · ціна · фото. 4. Статистика: расход
упаковки по заказам за период.

**Действия.** Упаковка списывается в заказ при сборке (менеджер отмечает
использованное); пополняется поставкой как товар. Низкий остаток — в счётчик
«потребує уваги».

**Фильтры и статусы.** Пошук по назві/артикулу; собственных статусов нет.

**⚠ Открытое.** нет.

#### 4.2.7 «Поставки»

**Назначение.** Передача товара на склад: план, трекинг, история приёмки.
**Кто видит.** CO, Оп, Пг (по §3.3).

**Блоки.** 1. Заголовок; справа «Додати нову поставку» (primary). 2. Статус-чипы
§5.3. 3. Фильтры: дата з/по · номер поставки · ТТН · спосіб доставки · статус.
4. Таблица: номер · дата створення · очікувана дата · статус · спосіб доставки ·
ТТН · кількість товарів / одиниць · коментар. 5. Деталка: состав
(заявлено/факт), расхождения, акт (#15), фото, журнал статусов.

**Создание поставки**: спосіб доставки (Нова Пошта / самостійна доставка на
склад / забір зі складу — «інше» по договорённости) · ТТН (с подсказкой, как
заполнять) · очікувана дата · коментар · товары: выбор из каталога, импорт
Excel, «Додати новий товар» прямо из формы (карточка §4.2.5, товар сразу
появляется в списке выбора) · кількість по каждой позиции.

**⚠ Открытое.** #15 (форма акта), #29 (компенсация при утрате на складе).

#### 4.2.8 «Статистика товарів»

**Назначение.** Продажи и движение товаров клиента за период. **Кто видит.**
CO, Оп (без прибутку), Пг (как Оп).

**Блоки.**

1. Фильтры: дата з/по · пошук по SKU · категорія · бренд · статус
   (активний/низький залишок/неактивний).
2. Сводка: SKU всього · в наявності · низький залишок · продано за період:
   дохід и чистий прибуток (прибуток — только CO; «середню оборотність»
   не делаем — отказ заказчика в видео, §9).
3. Динаміка продажів: штук · виручка · прибуток (графики).
4. Рух товарів за період: прихід · відправлено · повернення.
5. Топ-5 за продажами (+«переглянути всі»).
6. Товари без руху: артикул · назва · днів без руху · залишок (#52).
7. Таблица всех товаров со статистикой.

**Действия.** «Переглянути всі» у топа — полный список; клик по товару —
карточка §4.2.5; «товари, що закінчуються» — переход к залишкам §4.2.5.

**⚠ Открытое.** нет.

#### 4.2.9 «Фінанси»

**Назначение.** Постоплатные расчёты клиента (#19, #55): счета, операции,
тарифы. **Кто видит.** Только CO (§3.5).

**Блоки.**

1. Сводка: поточний рахунок за період (накоплено проводками) · заборгованість
   по виставленим рахункам · термін оплати.
2. «Рахунки»: таблица (номер · період · сума · статус: виставлений /
   сплачений / прострочений · дата) + скачивание счёта.
3. «Історія операцій»: фильтры (дата з/по · тип операції · номер замовлення /
   поставки / повернення) · таблица (час · тип · сума · коментар) · деталка
   операции: связанный объект (deep-link), строка тарифа и формула расчёта
   (прозрачность вместо «поверьте на слово») · «Експорт в Excel».
4. «Тарифи»: действующая версия тарифа клиента построчно (обробка замовлення ·
   приймання · зберігання · повернення по типам · додаткові послуги) с датами
   действия.

Блока «баланс / поповнити» нет — расхождение с видео зафиксировано (§9, ↷).

**⚠ Открытое.** #28 (что блокировать при неоплате и через сколько дней).

#### 4.2.10 «Підтримка»

**Назначение.** Встроенный чат клиент ↔ дежурный менеджер (#54). **Кто видит.**
CO, Оп; Пг — читает (§3.8).

**Блоки.** 1. Лента тредов (открытые/закрытые). 2. Тред: сообщения с автором и
временем; поле ввода; статус «менеджер на зміні» (имя). 3. Кнопка «Нове
звернення» с необязательной привязкой к заказу/поставке/возврату — привязка
даёт менеджеру мгновенный контекст.

**Действия.** Непрочитанные — бейдж в меню; уведомление менеджеру — в складском
контуре (§4.3.6). История хранится без срока.

#### 4.2.11 «Команда»

**Назначение.** Сотрудники клиента и их доступы (#65). **Кто видит/правит.**
CO (§3.7); Оп и Пг видят список без права правок.

**Блоки.** 1. «Запросити співробітника» (email + пресет). 2. Таблица: ім'я ·
email · телефон · пресет (Власник / Оператор / Перегляд) · статус (активний /
запрошений / деактивований) · последний вход. 3. Карточка: смена пресета,
деактивация, повторное приглашение.

Пояснение пресетов — прямо на экране, у каждого пункта. Права читаются из БД
при каждом запросе, а не из снимка в сессии: смена пресета действует немедленно,
деактивация — немедленно **и** завершает все активные сессии сотрудника.

#### 4.2.12 «Інтеграції»

**Назначение.** Подключение внешних источников заказов (#13). **Кто видит.**
CO; Оп — только просмотр статусов.

**Блоки.** 1. Сетка карточек: назва · статус (не підключено / потребує
налаштування / підключено / помилка) · дата последней синхронизации. Состав
карточек на старте: CRM (SalesDrive, KeyCRM, Хорошоп — по мере реализации),
Prom, Rozetka; карточки — реестром модулей, добавление интеграции не трогает
экран. 2. Карточка интеграции: учётные данные (шифруются, #40) · «Перевірити
з'єднання» · журнал синхронизаций и ошибок (питает «Помилки» #57) · «Призупинити».

**⚠ Открытое.** #43 (идемпотентность вебхуков), #59 (карта статусов НП).

#### 4.2.13 «Налаштування»

**Назначение.** Профиль клиента и параметры кабинета. **Кто видит/правит.**
CO (§3.5, §3.7); экран рендерится из реестра настроек (`docs/03-ux-ui.md`) —
новая настройка появляется здесь без правки экрана.

**Блоки (группы реестра).**

1. **Профіль бізнесу**: назва магазину · юрособа/ФОП · ЄДРПОУ/ІПН · контакти.
2. **ФОП-профілі відправника**: список, «Додати ФОП» (назва · дані ФОП · ключ
   API Нової Пошти — шифруется #40, показывается только последними символами) ·
   «зробити типовим» (последний использованный становится типовым
   автоматически).
3. **Сповіщення**: расписание email-дайджеста низких остатков — частота/дни
   недели (#51) · получатели.
4. **Безпека**: смена пароля · активные сессии («вийти з усіх пристроїв») ·
   журнал входов.

### 4.3 Складской контур

Общее: контур tablet-first (работа у полок), крупные элементы, сканер-паттерн —
`docs/03-ux-ui.md`; все экраны кросс-аккаунтные через `StaffScope` (§2).

#### 4.3.1 «Черга збірки»

**Назначение.** Живая очередь заказов на сборку с SLA-таймерами; главный экран
менеджера. **Кто видит.** O, M.

**Блоки.**

1. Шесть виджетов: очікує збірки · збирається · передано на НП · зібрано
   сьогодні · товарів взято сьогодні · моя комісія за день.
2. Таблица очереди (сортировка по залишку часу): номер замовлення · час
   надходження · клієнт (account) · кількість товарів · залишилось часу
   (живой таймер) · пріоритет §6 (цветом) · статус · менеджер (кто собирает) ·
   ТТН · действие.
3. Кнопки строки: «Взяти в роботу» (свободный заказ) → §4.3.2 · серые «Збирає
   Ім'я» (занят) · «Зібрано Ім'я» (завершён).
4. «Мій результат за день»: замовлень · товарів · комісія грн.
5. «Результати менеджерів»: ім'я · замовлень зібрано · товарів · комісія
   (каждый видит цифры всех — так в видео заказчика).

**Действия.** «Взяти в роботу» атомарно: два менеджера не могут взять один
заказ; после взятия заказ помечается именем. Комиссия считается по ставке
менеджера от комиссии клиента (#47) и появляется в виджете сразу после
завершения сборки.

**⚠ Открытое.** #35 (приоритет при пике: FIFO или по клиенту), #47 ↷.

#### 4.3.2 «Екран збірки замовлення»

**Назначение.** Пошаговая сборка одного заказа. **Кто видит.** O, M (взявший —
редактирует; остальные — просмотр).

**Блоки.**

1. Шапка крупно: номер замовлення · клієнт · пріоритет (цвет, живой) ·
   статус · залишилось часу.
2. Позиции: фото · артикул · назва · комірка · кількість — кнопки «Зібрано /
   Не зібрано» на позицию; комплект разворачивается в компоненты (#24);
   «віртуальний» товар — пометка «не зі складу», сборки не требует (#50).
3. Кнопка «Сканувати штрих-код» — закладка наперёд (обязательна в макете,
   активируется позже; из транскрипта).
4. Пакування: отметить использованную упаковку (#60).
5. Коментар до замовлення (от клиента) — всегда на виду.
6. Панель ТТН: номер, адрес, получатель — печать этикетки.
7. Действия: «Завершити збірку» (все позиции отмечены) · «Проблема»
   (комментарий обязателен → статус ERROR, таймер стоит, #48, #57) ·
   «Призупинити» (комментарий обязателен, таймер стоит, #48).

**Действия и эффекты.** «Завершити» → заказ ASSEMBLED, комиссия в проводку
(#1), возврат в очередь §4.3.1; отметка «передано перевізнику» — из очереди
(первая стадия финиша #4).

#### 4.3.3 «Приймання поставки»

**Назначение.** Приёмка и размещение поставки клиента. **Кто видит.** O, M.

**Блоки.** 1. Список поставок в статусах «В дорозі»/«Отримана» с ожидаемыми
датами. 2. Режим приёмки (сканер-паттерн): позиция → факт (скан или ввод) ·
расхождения подсвечиваются · фото повреждений. 3. Замер объёма товара при
первой приёмке — обязательное поле, без него хранение не тарифицируется (#58,
#2). 4. Размещение: позиция → комірка (#9). 5. Итог: акт приёмки; при
расхождении — акт расхождений (#15) с уведомлением клиента.

**Эффекты.** Завершение приёмки → поставка RECEIVED; завершение размещения →
PLACED, остатки оприходованы движением SUPPLY_IN по коміркам, и **в этот же
момент — единственная проводка «приймання поставки» по фактическим единицам**
(#3, §5.3): до PLACED начисления нет, повторного начисления не существует.

#### 4.3.4 «Інвентаризація»

**Назначение.** Сверка «система vs факт» (#25). **Кто видит.** O, M (§3.6).

**Блоки.** 1. «Нова сесія»: охват (весь склад / клиент / категория / комірка).
2. Режим подсчёта (сканер-паттерн): позиция · комірка · системна кількість ·
фактична кількість. 3. Итог сессии: таблица расхождений (позиция · система ·
факт · дельта · сума по собівартості — видна O). 4. «Застосувати»: корректировки
уходят движением ADJUSTMENT с привязкой к сессии; владелец получает сводку.

#### 4.3.5 «Повернення (склад)»

**Назначение.** Приём и разбор возвратов на складе (§5.2). **Кто видит.** O, M.

**Блоки.**

1. Очередь возвратов в статусе «Очікується повернення» (по ТТН возврата).
2. Приём: скан/поиск ТТН → состав заказа · фото посылки и формуляра ·
   по каждой позиции состояние: без дефектів / пошкоджений / відсутній.
3. Решения по позициям: «повернути в залишок» (движение RETURN_IN в комірку) ·
   «списати» (WRITE_OFF, фото обязательно, #33).
4. Блок «Прострочені рішення»: возвраты в «Очікує рішення», по которым клиент
   не ответил в срок (настройка склада, §3.4 ○¹) — менеджер принимает решение
   отсюда, действие пишется в комментарии возврата с пометкой «за таймаутом».
5. Завершение → возврат «Опрацьовано», проводка тарифа возврата по типу (#22),
   заказ → RETURNED (§5.1).

#### 4.3.6 «Чати підтримки»

**Назначение.** Входящие обращения клиентов (#54). **Кто видит.** O, M.

**Блоки.** 1. Тумблер «Я на зміні» (§3.7): дежурный получает новые треды.
2. Список тредов: клієнт · тема/превью · привязанный объект (замовлення/
поставка/повернення — мгновенный контекст) · непрочитанное · время. 3. Тред:
переписка + панель контекста привязанного объекта (статус, состав, ссылка).
4. Действия: ответить · закрыть · передать другому менеджеру.

#### 4.3.7 «Заявки клієнтів»

**Назначение.** Очередь онбординга новых клиентов (#14, §5.4). **Кто видит.**
O, M (§3.9).

**Блоки.**

1. Фильтры: статус (Нова / В роботі / Потрібні зміни / Підключено /
   Відхилено) · дата · відповідальний.
2. Таблица: дата · назва магазину · контакт (email/телефон) · очікуваний
   обсяг замовлень · джерело («звідки дізнались») · відповідальний · статус ·
   коментар.
3. Карточка заявки: данные регистрации · переписка/заметки · действия: «Взяти
   в роботу» · «Потрібні зміни» (комментарий клиенту, → NEEDS_CHANGES) ·
   «Підключити» (→ ACTIVE: кабинет открывается, письмо клиенту) · «Відхилити»
   (причина, §3.9).

#### 4.3.8 «Клієнти»

**Назначение.** Все подключённые account'ы. **Кто видит.** O, M.

**Блоки.** 1. Таблица: назва · статус онбординга · обсяг за місяць (замовлення,
м³) · тариф (версия) · контакти · дата подключения. 2. Карточка клиента: сводка
объёмов · тариф (O — правит, §3.5) · команда · ФОП-профили (без ключей) ·
переходы в его заказы/поставки/возвраты/финансы (через `forAccount`, §2;
финансы — только O).

#### 4.3.9 «Тарифи й комісії» (только O)

**Назначение.** Экономика склада. **Кто видит.** Только O (§3.5).

**Блоки.**

1. Тарифы клиентов: по клиенту — версии с датами действия (#6), строки услуг
   (обробка · приймання · зберігання · повернення по типам · додаткові
   послуги); «Нова версія» — копия текущей с правками, старая закрывается
   датой.
2. Ставки комиссий менеджеров: по менеджеру — версия ставки (%, от комиссии
   клиента, #47 ↷) с датой действия.
3. Журнал пауз SLA (#48): дата · замовлення · менеджер · тип (проблема/пауза) ·
   тривалість · коментар · действие «Анулювати» (пересчитает SLA заказа задним
   числом).
4. Штрафные нули SLA (#7): список просроченных с суммой недополученного.

#### 4.3.10 «Звіти» (только O)

**Назначение.** Срезы владельца. **Кто видит.** Только O.

**Блоки (первый состав, расширяется реестром виджетов).** 1. Обороты по
клиентам за период (замовлення · одиниці · нараховано грн). 2. SLA: медиана и
хвост времени сборки, доля просрочек, паузы по менеджерам. 3. Комиссии
менеджеров за период. 4. Склад: занятые м³ по клиентам (снимки #2), динамика.
5. Возвраты по типам и клиентам. 6. Списания (#33).

## 5. Машины статусов

### 5.1 Заказ — образец формата (18 статусов: DRAFT + 17, #49)

Триггеры: К — клиент (CO/Оп), М — менеджер, С — система (вебхук/воркер НП),
В — владелец. Эффекты: Р — резерв, Д — деньги/проводки, SLA, У — уведомления.

| Статус UA | enum | Кто/триггер | Откуда | Эффекты |
|---|---|---|---|---|
| Чернетка | `DRAFT` | К: «Зберегти чернетку» | — | нет резерва, складу не виден (#56) |

| В очікуванні дзвінка | `AWAITING_CALL` | К: флаг «дзвінок перед збіркою» | NEW | SLA: не идёт; в очередь не попадает |

| Помилка | `ERROR` | С: ТТН/адрес/вебхук; М: брак (#57) | NEW…ASSEMBLED | SLA: стоит; У: счётчик «потребує уваги» у клиента и склада |

| Відмова | `REFUSED` | С/М | AT_BRANCH, IN_TRANSIT | открывается возврат типа «відмова» (#22) → §5.2 |
| Потрібно повернення | `RETURN_NEEDED` | К/М: возврат після вручення | DELIVERED, COD_RECEIVED | открывается возврат типа «після вручення» (#22) → §5.2 |
| В очікуванні повернення | `AWAITING_RETURN` | С/М | REFUSED, RETURN_NEEDED | — |
| Повернення отримано | `RETURN_RECEIVED` | М: возврат прибыл на склад | AWAITING_RETURN | — |
| Повернено | `RETURNED` | М: возврат обработан | RETURN_RECEIVED | Р: возврат в остаток или списание (§5.2); Д: тариф обработки возврата (#3, #22) |

| Скасований | `CANCELLED` | К/М по матрице §3-обр | DRAFT…ASSEMBLED (#27) | Р: резерв освобождён; Д: по #27 ↷ |

### 5.5 Задача сборки (#48)

| Статус | Кто/триггер | Откуда | Эффекты |
|---|---|---|---|
| `QUEUED` | С: заказ стал NEW/CONFIRMED | — | таймер SLA идёт (рабочие минуты §6) |
| `IN_PROGRESS` | М: «Взяти в роботу» (атомарно) | QUEUED, PAUSED | закреплён менеджер |
| `PAUSED` | М: «Призупинити» + комментарий | IN_PROGRESS | таймер стоит; запись в журнал пауз (§4.3.9) |
| `PROBLEM` | М: «Проблема» + комментарий | IN_PROGRESS | таймер стоит; заказ → ERROR (#57); счётчики «потребує уваги» |
| `ASSEMBLED` | М: «Завершити збірку» (все позиции) | IN_PROGRESS | Д: комиссия менеджера (#47); заказ → ASSEMBLED |
| `HANDED_OVER` | М: «Передано перевізнику» | ASSEMBLED | SLA-финиш стадия 1 (#4); ждёт скан НП |

Аннулирование паузы владельцем (§3-обр) не меняет статус — пересчитывает
SLA-время задним числом и помечает запись в журнале.

Соответствие машине заказа (§5.1): `QUEUED` — заказ в `NEW`/`CONFIRMED` ·
`IN_PROGRESS`/`PAUSED` — статус заказа не меняется (пауза — свойство задачи) ·
`PROBLEM` — заказ переводится в `ERROR` и возвращается из него при снятии
проблемы · `ASSEMBLED` — заказ `ASSEMBLED` · `HANDED_OVER` — флаг
`handedOverAt` на отправлении; статус заказа станет `IN_TRANSIT` только по
скану НП (стадия 2, #4). Других комбинаций не существует.

## 7. Финансовый контур

**Цикл постоплаты (#19):** проводки накапливаются за период → в конце периода
система формирует счёт из проводок → счёт «виставлений» уходит клиенту
(email, #39) → оплата на счёт → владелец подтверждает → «сплачений»; не оплачен в срок →
«прострочений» (что блокируется — #28, до ответа не блокируется ничего,
просрочка только подсвечивается).

**Типы проводок** (знак с точки зрения клиента: `+` — начислено к оплате):

| Тип | Триггер | Сумма |
|---|---|---|
| Обробка замовлення | сборка завершена (§5.1 ASSEMBLED) | по факту: 20 грн + 1 грн/од. сверх первой (#1) |
| Приймання поставки | поставка PLACED (§5.3) | 1 грн × фактические единицы (#3) |
| Зберігання | ежемесячно воркером | 385 грн/м³ × средний объём по ежедневным снимкам (#2, объём — #58) |
| Обробка повернення | возврат PROCESSED (§5.2) | по типу возврата, дефолт 12 грн (#22 ↷) |
| Додаткова послуга | услуга «Виконаний» (§5.6) | из заявки (#17); листовка 2,5 · проверка 2 · фотоотчёт 4 (#3) |
| Штрафний нуль SLA | просрочка SLA (§6, #7) | 0 грн вместо обработки; видна владельцу отдельным списком |
| Коригування | вручную O (§3.5), комментарий обязателен | любая, ± |
| Оплата рахунку | подтверждение оплаты | − сумма счёта |

Каждая проводка хранит ссылку на объект (замовлення/поставка/повернення/
послуга), строку тарифа и зафиксированную цену (#6) — деталка операции в
§4.2.9 показывает формулу, а не только итог.

**Комиссии менеджеров (#47 ↷):** база — проводка «обробка замовлення» этого
заказа; ставка — процент, версия на менеджера (§4.3.9); начисление — в момент
завершения сборки; менеджер видит свои (§4.3.1), владелец — все. При штрафном
нуле комиссия менеджеру тоже не начисляется — кроме случая, когда просрочка
покрыта аннулированной паузой «не с нашей стороны» (#48): тогда решает владелец.

## 8. Аутентификация и безопасность

Провайдер — better-auth: решение принято, строка в `docs/06-architecture.md`,
пункт #44 закрыт. Реализация — `[contract]`, задача 1.4.

- Пароли — argon2id, длина ≥ 12.
- Токены сброса/подтверждения одноразовые, TTL ≤ 1 ч, в БД хешированы; ответы

  клиента (#66).
- Ключи НП — прикладное шифрование (#40); ПДн получателей — отдельная таблица
  с обезличиванием (#18).
