## Этап 1 — Нитка «Товар завёлся» (один человек, блокирует всё)

Владелец: **alex** (делал каркас и слой доступа; контекст уже в голове).

Нитка — вертикальный срез через все архитектурные компоненты сразу:

```text
вхід клієнта → створення товару (SKU, назва, ціна) → список «Товари»
   → той самий товар у кабінеті складу → чужий товар не видно
```

Чем она ценна: проходит по сессии, `AccountScope`, `StaffScope`, Prisma,
настоящей миграции, форме с zod, server component и деплою в прод одним путём.
И проверяет главный риск проекта — доступ к чужим данным — раньше, чем на нём
успеет вырасти второй контекст.

| Задача | Содержание | DoD сверх общего |
|---|---|---|
| 1.1 Зависимости UI | Tailwind + shadcn/ui — **отдельный маленький PR первым** (правило нового пакета) | строка-решение в 06-architecture |
| 1.2 Зависимость auth | better-auth, отдельным PR; пункт #44 закрыт. `[contract]` | строка-решение в 06-architecture |
| 1.3 Схема нитки | `Account`, `AccountMembership`, `StaffMember`, `Product` + таблицы better-auth; первая настоящая миграция, с неё же действует `expand/contract` (#37 — П1, «до первой таблицы»). `[contract]` | `migrate status` чист; контрактные тесты обоих scope |
| 1.4 `StaffScope` | второй примитив в `packages/db` рядом с `AccountScope` (06-architecture) | тесты: кросс-аккаунтная выборка без утечки чужих объектов |
| 1.5 Вхід і вихід | форма входа, серверная сессия, редирект по роли (02 §8) | `/security-review` + semgrep до мержа; rate limiting проверен тестом |
| 1.6 Два layout | кабинет клиента и кабинет склада, без реестров и settings-движка (03 §2) | инвентарь состояний по 03 §3 |
| 1.7 «Товари» у клиента | создание с zod-схемой и список своего аккаунта | одна схема на форму и на API |
| 1.8 Тот же товар у склада | список товаров всех клиентов через `StaffScope` | видно, чей товар |
| 1.9 Нитка целиком | сквозной тест Playwright + деплой в прод | тест: клиент не видит товар чужого аккаунта ни в списке, ни по прямой ссылке; склад через `StaffScope` видит товары всех аккаунтов |

Нитка сознательно не делает: реестр модулей, реестр виджетов, settings-движок,
регистрацию, восстановление пароля, подтверждение почты, машину онбординга,
комплекты, пороги, категории, картинки, импорт Excel. Всё это приходит
следующими срезами — каждый добирает из 04/05/06 ровно то, что нужно ему.

Пока идёт этап 1, **step** ведёт подготовку своего контекста: ревью 04/05 по
своим доменам, прототип импорта Excel (parsing, без UI), и возвращает смоук-тесты
Playwright отдельным PR (закрытый PR #23). Требование DoD про документ на этот PR
не распространяется: тест закрепляет сценарий задачи 1.9, уже описанный там,
и нового поведения не вводит.

## Ритм и синхронизация

- Ветка живёт максимум день; утром `git fetch && git rebase origin/main`.
  Незаконченное — за feature-флагом. Реестр модулей поддерживает их из коробки,
  но появляется он задачей 2.0 — до неё флаг заводится вручную.
- Правки схемы Prisma и общих реестров — `[contract]`, маленькими PR, первыми.
- Каждая задача таблиц выше = один issue в GitHub со ссылкой на §04/§05/§06;
  issues создаются после мержа этого PR, назначение — по колонке «владелец».
- Definition of Done — из `AGENTS.md`; для UI-задач дополнительно инвентарь
  состояний (03 §3); для auth и всего, что трогает деньги/права, —
  `/security-review` до мержа.
- Пятница — сверка бэклога: что разблокировали ответы заказчика, что
  переносится. Решения — в 06-architecture, вопросы — в 09-findings-backlog,
  личное «что сделал» — в PROGRESS.
