# 03 — Онбординг клиента

## Цель

За один понятный проход довести новый магазин от заявки до первой рабочей
операции, не создавая доступ к чужим данным и не заставляя клиента повторно
вводить уже подтверждённые сведения.

Онбординг описан на уровне поведения продукта. Реализация экранов и API будет
следующим этапом после закрытия вопросов из `docs/findings-backlog.md`.

## Обязательный путь клиента

```text
Регистрация
  → подтверждение контакту
  → заявка на підключення
  → перевірка менеджером
  → доступ до кабінету
  → профіль магазину та команда
  → товари / SKU або імпорт
  → перша поставка
  → перше замовлення
```

### 1. Регистрация

Клиент создаёт заявку на подключение самостоятельно. До решения менеджера ему
доступен только экран ожидания и собственные данные заявки. Рабочие данные
склада и других клиентов недоступны.

### 2. Проверка менеджером

Менеджер видит новую заявку, проверяет её и подтверждает подключение либо
возвращает на уточнение. До подтверждения клиент не может отправлять реальные
заказы в обработку.

Конкретные поля заявки, причина отказа и необходимость отдельного подтверждения
контакта ещё требуют решения. Их нельзя молча закреплять в API или схеме БД.

### 3. Первый вход

После подтверждения клиент попадает на пошаговый мастер. На каждом шаге есть
один следующий результат и возможность вернуться к уже сохранённому шагу.

| Шаг | Результат |
|---|---|
| Профиль магазина | Заполнены название и рабочие реквизиты, доступные клиенту |
| Команда | Приглашены сотрудники и назначены минимально необходимые права |
| Товары | Добавлены первые SKU или подготовлен импорт |
| Поставка | Создана первая поставка для приёмки |
| Заказ | Создан или импортирован первый заказ |
| Готово | Пользователь видит, куда вернуться для следующей операции |

Шаги, которые пока невозможно выполнить из-за незакрытого вопроса, должны
показывать причину и сохранённое состояние, а не создавать фиктивные данные.

### 4. Интеграции

Интеграция с Новой Поштой и CRM — необязательная часть базового пути. Клиент
может начать с кабинета, а подключение интеграции выполнить позже. Ключи
интеграций принадлежат клиенту, хранятся защищённо и не показываются повторно в
открытом виде.

## Путь менеджера склада

```text
Нова заявка
  → перевірка
  → підтвердження клієнта
  → перевірка тарифу та реквізитів
  → контроль першої поставки
  → контроль першого замовлення
```

Менеджер не должен вручную создавать клиента в таблице и параллельно выдавать
доступ в чате: источником состояния подключения становится кабинет. События
подтверждения и изменения доступа должны попадать в журнал действий.

## Минимальные состояния онбординга

Названия приведены для согласования; это не обязательные имена enum.

```text
new → contact_pending → manager_review → needs_changes
                                  └──────→ approved → active
                                  └──────→ rejected
```

Состояние заявки и состояние готовности мастера — разные вещи. Подтверждённый
клиент может временно не иметь товаров или первой поставки, но это не означает,
что его доступ снова нужно отправлять на проверку.

## Критерии готовности онбординга

- клиент видит только свой `account`;
- менеджер может принять решение по заявке и оно сохраняется;
- повторный вход продолжает мастер с последнего незавершённого шага;
- уже сохранённые данные не теряются при возврате назад;
- клиент понимает, что делать после завершения каждого шага;
- интеграции не блокируют старт без интеграции;
- в журнале есть создание заявки, решение менеджера, приглашение пользователя
  и изменение прав.

## Открытые решения

До разработки нужно уточнить: каким каналом подтверждается контакт, какие поля
обязательны в заявке, кто кроме менеджера может подтверждать клиента, какие
реквизиты нужны для первой поставки и можно ли создать заказ до приёмки первой
поставки. Связанные вопросы по саморегистрации и ролям находятся в
`docs/findings-backlog.md`.
